## The follow-up batch (round two) — written, verified, uncommitted

Five reports from the owner playing the shipped tier. Each is listed with what was actually wrong, since three of the five turned out to be a different problem than the report described.

**1. The ally-decay footer showed the wrong tier's badge.** Symbiote inherits Arachnid's happiness-drain cost, and §9's attribution rule is *emoji-only* — the copy never names a tier — so the badge is the entire signal for whose subscription is talking. A Symbiote subscriber was being shown an Arachnid badge on their own drawback. Now `tier_badge(tier_rank)`: the viewer's own tier. **Note the command**: this footer is in `/ally check`, not `/ally visit` (which has no tier footer at all).

**2. Arachnid+ perks in the shop now show both badges.** Same table, opposite row: a *static catalog* answers "who is this available to?", so it lists **every** badge that clears the gate (`tier_requirement_badges(min_rank)`). Showing only Arachnid told a Symbiote subscriber they couldn't buy something they could. These two fixes are one rule with two halves, now written into §9 as a table — and both bugs came from the same wrong assumption, that the gate's tier and the player's tier are the same thing. For a superset tier they never are.

**3. The Spider Bots report was three separate things, and the break path wasn't one of them.** The report was "they don't get removed from the inventory." They did — `roll_gadget_wearout` deletes and commits correctly. What the live dev DB actually showed was **two** `spider_bots` rows for that user, both unequipped: spares from separate purchases. `/inventory` rendered them as two byte-identical `x1 (100 durability)` bullets, so losing one changed nothing visible. Three fixes:
   - Render-identical rows fold into one line with quantities summed, and `(Lv. N)` now appears so genuinely-different copies stay distinct.
   - **"Swinging-Grade" is gone** (with "Battle-Grade"), replaced by "Equipped"/"Stowed". The owner's read was exactly right: those were slot states dressed up as *item quality grades*, and no such grades exist. Spider Bots are combat gear whether or not they're in a slot.
   - One **real latent bug** found along the way: a `quantity > 1` gadget row was deleted **wholesale** by a single break. Now it decrements. Only reachable via `/admin` grants or seeded data (the shop never stacks gadgets), which is exactly why nobody would have connected the loss to a break.

**4. Every camera mention now shows the camera they own.** Patrol cards, `/bugle photos` and the photo-bump row all drew the base beat-up 35mm, and one line hardcoded the words *"the silver lens"* — so a Symbiote subscriber on a $3,000 Gold body saw someone else's equipment on every photo. The camera now resolves **once, server-side** (`BattleReport.camera_item_key`/`.camera_label`, set in `finalize_battle`, which is the only place with both the session and the live tier check) and travels with the result. `EffectiveCamera.label` reads `Item.name` from the database rather than hardcoding a string, so shop, inventory and battle copy can't drift apart.

**5. Perks are revoked at use time, for both lapsing and unlinking.** One live rank check covers both, and that's the whole design: a cancelled pledge clears the stored tier (`refresh_stale_links`) and `/patreon unlink` deletes the row, so `get_tier_rank` returns rank 0 either way — nothing needs to tell them apart. `patreon_service.locked_item_keys()` is the shared query and short-circuits without a DB round-trip when nothing in the list is gated, which is the normal case. Two enforcement points: `list_usable_gadgets` (gadgets) and `get_effective_camera` (cameras).

Three decisions inside #5 worth not re-litigating:

- **Inert, not deleted.** A locked gadget keeps its row, slot and upgrade level. Resubscribing switches it back on rather than asking someone to re-buy gear they paid cash for — but the load-bearing reason is the slot: hiding it from `list_equipped_gadgets` would free one, let them equip a third gadget, and hand them **three live gadgets** on resubscribe. Hence the split between "what's equipped" (honest, feeds `MAX_EQUIPPED_GADGETS`) and "what may fire".
- **A locked gadget can't break; a locked camera can.** Deliberate asymmetry. The gadget does nothing, so breaking it would make lapsing *destroy* gear instead of pausing it. The camera is still earning photos at base stats, so it carries base-camera risk — making it invulnerable would turn lapsing into its own perk.
- **Revocation is made visible, and cash spend on inert gear is blocked.** Scope taken on beyond the literal report, because the button-suppression makes a revoked gadget *more* invisible, not less — one that silently never fires is indistinguishable from a broken one. So `/gadget status`, `/gadget panel`, `/inventory`, autocompletes and Select descriptions all label it. `upgrade_gadget` rejects with its own message rather than reusing the equipped-list filter, which would say "that gadget isn't equipped" about a gadget visibly in a slot — and this is a **cash spend**, the worst version of the bug. Equip/Unequip stay live: freeing the slot is the one useful action.

`/inventory` is the only surface that explains a revoked **camera** — cameras have no status command of their own.

**Also moved**: `GATED_ITEM_MIN_RANK` migrated from `shop_service` to `patreon_service`. Use-time enforcement gave it a second consumer, and a map that both the shop and the battle loop read belongs with the tier logic.

## Round three — the tier accent, and the upgrade welcome

Two pieces of work, both in the working tree alongside round two.

### The Patreon accent on every Components V2 panel

Subscribers had functional perks but nothing *visual*. Now every V2 container a subscriber sees carries their tier's colour as its accent bar: Arachnid `#A91D3A`, Symbiote `#707C8F`, no subscription = no bar (unchanged from before).

Two structural facts turned what looked like a 57-call-site sweep into ~14 real edits, and both are worth knowing before touching V2 code again:

- **`Container(colour=None)` is byte-identical to `Container()`.** pycord's `__init__` does `accent_color=colour or color` (`.venv/.../discord/ui/container.py:117`), so "no subscription" needed no special-casing anywhere — the free-account render is provably the same as it was.
- **`utils/v2_embeds.py` already funnelled 38 of 41 containers**, so all 36 `StaticView(...)` call sites across 16 cogs needed **zero** edits.

The design decision worth not re-litigating: the accent is resolved **once per command** into a `contextvars.ContextVar` (`utils/tier_accent.py`), set by the single global `before_invoke` hook in `utils/first_run.py`, and read by `utils.v2_embeds.make_container()`. Threading an `accent=` argument through 36 call sites would have meant 36 chances to miss one, and **a missed site is invisible** — a dropped accent renders exactly like a free account. This is safe because pycord's invoke path runs `call_before_hooks(ctx)` and then the callback in the *same* task, and each interaction gets its own task with its own copied context, so one user's colour cannot leak onto another's panel.

**The contextvar is dead inside component callbacks.** Button presses and `on_timeout` run later, in fresh contexts. So every interactive view captures `self.accent` at construction and re-renders from that field — nine of them do (`PaginatedView`, `LeaderboardView`, `GadgetPanelView`, `ShopBrowseView`, `HelpBrowserView`, `StartView`, `AdminHelpView`, `UserInfoView`, `AdminsListView`). Two sites needed more than the mechanical change: `PatrolBattleView` derives from the `tier_rank` it already received rather than adding a redundant field, and `help_cog`'s `OpenGuideButton.callback` — the one view in the codebase built outside a command body — forwards the accent captured by the `StartView` the button lives on.

`accent_for_rank()` in `patreon_service` is an **exact-rank dict lookup, and must not become `>=`**. Every perk *gate* in that file uses `>=` because a gate asks "does this rank clear the bar", which Symbiote must satisfy for Arachnid gates. The accent asks "which tier *is* this player", which has one answer — a `>=` walk would paint Symbiote subscribers Arachnid red. There's a comment saying so, because someone will otherwise "consistency-fix" it.

Two accepted consequences:

- **Public messages carry the invoker's accent.** Most V2 responses are non-ephemeral, and a single Discord message cannot be coloured per-viewer. So `/admin userinfo @target` shows the **admin's** colour, not the target's. Confusing *viewer* with *subject* is exactly what caused round two's bugs #1 and #2, so it's worth stating rather than discovering.
- **One extra query per command, for everyone including non-subscribers.** `get_tier_rank` is a single `session.get(PatreonLink, discord_id)` — a primary-key lookup, on a session `first_run` was opening anyway. Deliberately uncached: a cache would delay perk *revocation*, which is the thing round two just fixed.

**`/v2demo` is deleted** rather than made tier-aware (`cogs/v2_demo_cog.py` removed, `bot.py`'s `EXTENSIONS` 23 → 22). It was a temporary scope demo. It held 638 uncommitted lines, so a copy is parked at `scratch/v2_demo_cog.py.removed` (gitignored) — delete that once you're sure. The memory note that pointed future sessions at it as "the working reference" has been rewritten, since a pointer to a deleted file is worse than no pointer.

**Miss-guard for anyone adding a panel**: `grep -rn "discord\.ui\.Container(" .` must match **only** `utils/v2_embeds.py`. Any other hit is a panel that silently renders without a subscriber's colour. It's clean right now.

### The link-then-subscribe welcome

Someone who links Patreon *before* pledging gets the "Patreon Connected, nothing active yet" card — correct at the time. When the pledge lands, there's no interaction for the bot to respond to, and `handle_callback` has already stamped `last_checked_at`, so the background loop wouldn't look again for six hours and when it did it **only logged**. Perks switched on in silence; the sole recovery was re-running `/patreon link`, which nobody does after it already worked once.

Both halves are now closed:

- **A second staleness window.** A link with `tier IS NULL` has nothing to revoke — the only change it can produce is a *grant*. Making that wait six hours gets the asymmetry backwards: being slow to revoke protects someone who is paying, being slow to grant just strands them. Tier-less links go stale after `REFRESH_PENDING_STALE_AFTER` = **20 minutes**, bounded by `REFRESH_PENDING_WINDOW` = **48 hours** since linking. The bound is load-bearing: `refresh_link` *also* nulls the tier on a dead grant (`_DeadLinkError`), and a row sitting tier-less for days is far likelier to be one of those — or someone who linked and never pledged — than a pledge about to land. No dead-link flag is persisted, so link age is the only available discriminator.
- **`patreon_tier_upgraded`.** `patreon_tick` dispatches it whenever `outcome.rank_delta > 0`, and `PatreonCog.on_patreon_tier_upgraded` DMs the welcome for the user's current tier. Routed through the **event bus** rather than reaching into the cog for `_send_welcome`, for two reasons: the welcome copy stays owned by the cog that owns everything else about it, and because dispatch schedules the listener as its own task, a closed-DM `HTTPException` cannot take down a `tasks.loop` that dies permanently on one uncaught exception. No channel fallback, unlike `/patreon link`'s copy — nothing the user did triggered this, so a bounced DM just logs.

The 20-minute window sits deliberately *above* the 15-minute tick: a pending link comes up on roughly every other tick, so **20–35 minutes** from pledging to the DM. Dropping it under the tick interval wouldn't be faster, only more expensive — the queue can't drain more often than it runs. `/patreon link` remains the instant manual path, and is now commented as the fallback rather than the only route.

**A regression caught by the checks, worth remembering.** The first version of the query made the six-hour rule conditional on `tier IS NOT NULL`, with the fast lane as the other branch. That dropped tier-less links older than 48h out of the queue **entirely** — strictly worse than before the change, since the original query re-checked every row unconditionally. The fast lane has to be an *added* `OR` branch, never a replacement. The fixture row that caught it ("pending, linked 10d ago, checked 7h ago") exists precisely because the comment claimed a fallback the code didn't implement.

**The three combat changes were tuned as one package, not individually**, because they all move the same number: deleting the dampener is a buff, lowering Venom Blast's bar is *not necessarily* one, and the override changes are nerfs.

**Venom Blast's threshold is the most counter-intuitive number in this batch, and the sweep is why.** ⚠️ *Every win-rate figure in this paragraph was measured against the **automatic** mechanic round five replaced with a button; the reasoning that picked 25% survived that change and is why the button's arming bar is still 25%, but the numbers did not — see round five below.* The charge is once per fight, so a bar set high spends it on a survivable hit and leaves a lethal one later unabsorbed — bracket-10 win rate was genuinely **U-shaped** across `{0,15,25,35,50,65,80}`, every step more than 3σ. The optimum was 65% (a free +0.14% over shipping 0%) and it was **rejected anyway**: at that bar 78.6% of blasts fired on round 1–2, which turns a life-saving intervention into a routine opening move and makes "swallows the hit whole" dishonest. **25% shipped** — median round 4, only 10.6% firing on rounds 1–2, the last threshold that stays a mid-fight event. It was also the *worst* point on the win-rate curve (−9.06% at bracket 10), and that was a deliberate progressive trade: the cost landed only on high brackets where the blast already fired in 99.1% of fights, while low brackets gained both visibility (3.3% → 22.6%) and win rate. Symbiote at bracket 10 won 60.86% against 3.78% unsubscribed.

**The override's gadget hijack answers the objection that kept gadgets exempt, rather than overruling it.** The recorded reason was that gadgets are scarce and carry durability, so swallowing one "reads as a lost *item* rather than a lost impulse". So the branch sits at the very **top** of `resolve_gadget`, above `roll_gadget_effect` and `roll_gadget_wearout`: a hijacked press costs the round but **never the gadget**. `check_override.py` proves the placement by replacing both rolls with spies and asserting a hijacked press calls neither — a source read can't prove it, since an early return could still sit below a call.

Extending it to gadgets is also **what makes the override a real cost outside boss fights**, which it wasn't before: in a crime patrol suit integrity is cosmetic, so losing an Evade's damage reduction costs almost nothing, but losing a gadget's damage costs the same everywhere. At an unchanged 0.10 the crime cost went from **−0.51% to −2.36%** purely from the new surface. 0.15 measured at −6.30% on a boss (51% of fights see at least one hijack); **0.20 was measured at −8.76% and rejected** against the −7.87% bar. That bar had previously rejected 0.15 too — it only clears now because it was re-measured against the post-dampener configuration. ⛔ **Round five overturned all of this**: the owner asked for 0.30 directly, which breaks the −7.87% bar by a wide margin and was shipped anyway as an instructed decision. The bar is now a record of what was measured, not a gate anything passes.

**Biomorphic Webbing's ambient scavenge had to be a new leaf module.** `patrol_service` imports `ally_service`, so `ally_service` can never import back — `services/biomorphic_service.py` imports only `random`, `inventory_service.add_item` and one constant. A 20% roll on `/tutoring`, `/ally visit` and `/bugle submit` for one repair component (**raised to 30% in round six**), weighted 3:1 toward Spandex Fabric over the pricier Micro-Electronics, with activity-specific flavor. **Every call sits after the activity's own commit**, so a bonus can never roll back a completed activity.

**The repair reskin is copy-only and that's enforced by test, not by reading.** `/workbench` becomes "The Bond" for Symbiote subscribers — Peter doesn't understand the thing, but it still demands spandex and micro-electronics. `check_symbiote_repair.py` runs the identical scenario at all three ranks and asserts **one distinct outcome tuple** across them, so a copy change can't quietly become a mechanical one. **"Suit Integrity" was deliberately left alone** (a documented deviation from the plan, which listed it): it's the shared stat name and renders in `/balance`, the boss gate and `/admin profile`, so reskinning it in one panel of four would make one number look like two stats.

**Item 7 turned out to be an attribution rule, not an icon sweep.** Before it, the tier badge did two jobs — "a perk fired" and "whose subscription" — so a Venom Blast, a bonus component and a bonus photo all carried byte-identical attribution. Now the **perk's glyph leads** the line and the **tier badge trails** it, and the tier's name is never spelled out. Perks with no glyph of their own (the override, the repair reskin) correctly render the badge alone.

The one deliberate inversion is `/shakedown`: **Stealth Mode belongs to the victim, not the reader.** `ShakedownResult` now carries `target_tier_rank` because the cog physically cannot look it up off `ctx.author`. It's returned on the result rather than re-read in the cog because `get_tier_rank` consults the Patreon cache, which the background loop can move between the gate and the render — the badge has to name the rank the gate actually judged. Populated on **both** branches, since a field set on only one is a trap for the next caller.

## Round five — the camera, the button, and 0.30

Three requests, again with the instruction to take them one at a time. All three land on ground round four had just covered, and two of them **reverse** what round four decided.

**1. "I bought the Gold camera and I still see the Silver one in my inventory."** Round four's fix was real and its check script passed; the design was wrong. "Retire" meant *unequip and keep the row*, intended as a lapsed-pledge fallback. It never worked as one, and four separate facts each independently make the kept row unreachable: `get_equipped_camera` filters on `equipped`, **there is no `/equip` command** to turn it back on, `get_effective_camera`'s lapse path degrades the *equipped* body's stats rather than falling back to the retired row, and `economy_cog` only annotates a tool line when it's equipped or tier-locked — so a dead $1,000 Silver rendered next to the Gold looking exactly like working gear.

Offered labelling, hiding, refunding or deleting, and shown that deletion writes off $1,000, the owner chose **delete the row**. Three consequences worth carrying:

- **Deletion makes a downgrade purchase destructive**, so `buy_item` refuses one outright rather than allowing-and-guarding. A downgrade was already a pure loss before deletion (no equip command to switch back), it just wasn't a *destructive* one, so blocking it takes nothing of value away.
- **`CAMERA_FAMILY_KEYS` is ordered cheapest-first, and the list index IS the tier.** That's now load-bearing in three places — `get_equipped_camera`'s tiebreak, `install_tool`'s lower-tiers-only delete slice, and `buy_item`'s downgrade refusal. Reordering that list would silently make a $1,000 Silver purchase scrap a $3,000 Gold body.
- **A silent destructive write-off is the next bug report**, so it isn't silent: `install_tool` returns the keys it destroyed and both call sites render `scrap_note()` — *"Stripped Silver-Grade Camera for parts."* The shop descriptions in `data/items.json` were saying the old body was "retired", which was the same misleading word the code had used; both paid cameras now say the old one is gone, not stashed. (`db/seed.py`'s `seed_items()` upserts `description` on every startup, so that propagates to existing DBs with no migration.)

**The admin path had the same bug in a second form, and only running the code found it.** `/admin inventory give-item` names its local `scrapped_note` — because the first draft named it `scrap_note`, shadowing the imported function, so the first tool an admin granted would raise `TypeError: 'str' object is not callable`. `compileall` cannot see a runtime shadowing error and neither can a source read that isn't looking for it; the check script caught it in `shop_service` and the same mistake in `admin_cog` survived until it was read line by line. **This path has no automated coverage of its own** — `check_camera_gold` drives `install_tool` and `scrap_note` directly, not the cog.

**2. Venom Blast is a button now, and that makes it a much weaker perk.** It sits beside Evade in boss fights only, present from **round 1** in a greyed-out `Venom Blast — Not Charged` state, arming at ≤25% integrity and reading `Venom Blast — Spent` after use. Three states, all greyed but the middle one; `style=secondary` because it's the only style left (Attack owns `danger`, Evade `primary`, gadgets `success`) and grey happens to be right anyway — inert until it isn't. A button that only *appears* once armed couldn't teach anyone the condition exists, so it's always there and a subtext line under the row says what charges it.

The cost of the change is large and it is a direct consequence of the requested design, not a bug. At the same 25% bar, bracket-10 win rate goes **60.86% → 13.91%** against a 3.93% unsubscribed floor. The automatic version returned `damage=0` on the hit that would have ended the fight — it was a **once-per-fight death save** wearing a damage perk's copy. A button spends the same charge on *offense* while the lethal hit still lands. Getting the power back would mean giving the press a defensive component; nothing else moves that number.

Two things about the numbers:

- **An armed press is exempt from the suit override.** Asserted, not assumed — the check forces the override rate to 1.0 and fires 20,000 armed presses. A hijacked Venom Blast would consume the once-per-fight charge for nothing, which is the one override outcome that costs a *resource* rather than a round.
- **Every button-era figure is a floor, not an estimate.** `run_fight` presses the blast the round it arms — the greediest possible policy. A player who holds it reaches strictly better outcomes, so the sim under-reports the perk.

**3. The override rate is 0.30**, double round four's 0.15, as instructed. This knowingly breaks the file's own **−7.87%** bar and fails the round-four plan's first acceptance criterion (a paid tier must never be net negative). The measured cost, by press type — and **compare rates within a column, never across**, since delta magnitude scales with the baseline's headroom:

| rate | evade-only, boss | with gadgets, boss | evade-only, crime | with gadgets, crime |
|---|---|---|---|---|
| 0.10 | −2.16% | −10.59% | −0.51% | −2.36% |
| 0.15 | −3.28% | −15.91% | −0.80% | −3.73% |
| 0.20 | −4.64% | −20.16% | −0.89% | −4.87% |
| **0.30** | **−6.82%** | **−29.02%** | **−1.74%** | **−6.88%** |

What 0.30 buys is visibility: **1.20 hijacks per fight and 78.8% of fights showing at least one**, against 0.43/62.8% at 0.10. What it costs is concentrated almost entirely in the gadget hijack. Gadget-free, the Symbiote tier is net **−0.38% / +26.76% / +10.30% / +8.81%** at boss brackets 1/5/10/20; with three gadget presses a fight it's **−1.05% / −11.86% / −6.41% / −3.35%**. Crime patrols stay strongly positive either way (**+3.83% / +20.26% / +42.81%** across the three tiers). So the drawback lands hardest on the player who bought the most gear, which is backwards. **If this needs softening later, narrow the hijack back toward Evade-only rather than lowering the rate** — the rate is what makes the perk visible, and the gadget surface is what makes it expensive.

## Round six — Stealth Mode gets a face and a scoreboard, and the scavenge rate lands

Two asks. The first: *"if the stealth mode triggers, the embed should show the stealth mode emoji, symbiote branding etc etc. does that happen?"* The honest answer was **half yes**. Round four had already wired the glyph and the badge and pinned both by test, so the attribution rule was satisfied. Two things it hadn't touched turned out to matter more than the emoji. The second ask raised Biomorphic Webbing's ambient-scavenge rate, and is item 3 below.

**1. The panel was a refusal wearing a perk's glyph.** The branch called `error_embed`, which titles **all five** of `/shakedown`'s refusals *"Parker Luck."* — so the only Symbiote perk a thief will ever watch fire was framed as the thief's own bad luck. A legacy embed also can't carry the tier accent bar or a thumbnail, which are the two things that make a panel *look* paid for. It's now a `StaticView` titled **"Stealth Mode"** with the `stealth_mode` thumbnail. The other two branches were deliberately left alone: a successful shakedown was already a `StaticView`, and a *failed* one is a real refusal that `error_embed` fits.

**The trap inside that fix is the accent, and it is the kind that never looks broken.** `make_container()`'s default accent comes from an ambient `ContextVar` set once per command from the **invoking** user (round three's design, and the right default everywhere else). On `/shakedown` the invoker is the *thief*. Left to default, a subscribed thief would see **their own** tier colour on a message about somebody else's subscription, and an unsubscribed thief would see no bar at all on a panel whose entire subject is a subscription — and in both cases the panel renders cleanly, so nothing would ever be reported. So the branch passes `accent=accent_for_rank(result.target_tier_rank)` explicitly, and the check asserts both halves: that the accent is read off the target **and** that it is not read off the invoker. All three marks — glyph, badge, accent — now name the one person who paid.

**2. The perk had no surface for the person paying for it, and that's the part worth remembering.** A protected attempt answers the thief and tells the target *nothing* — no DM, no ping, not even a `transactions` row — and the gate only opens once the target has been idle 20+ minutes. A subscriber could hold the tier for a month, have a dozen shakedowns turned away, and have no way to learn any of it happened. Every other perk in the tier announces itself the moment it fires.

`/patreon perks` now reads it back: `count_stealth_protections()` counts the subscriber's `OUTCOME_PROTECTED` rows and the line becomes *"It's turned away 3 attempts so far — you weren't there to see any of them."* **No new table and no new write** — round one's threshold instrumentation (`shakedown_attempts`, migration `a7c41e93b508`) turned out to already be exactly the data its owner had a stake in; it was only ever being read by an analysis script. The welcome DM carries it too, since `/patreon link` re-sends that card on demand.

Four small decisions inside it:

- **Zero renders no clause at all**, not "blocked 0 attempts". A brand-new subscriber reading the welcome DM shouldn't be handed a nil stat about a perk they haven't had time to benefit from.
- **The 20 is interpolated from the constant, not typed into the copy.** Hardcoding it is exactly what went stale on the Venom Blast line when its multiplier moved, and on the ally-decay drawback before that. The check proves the copy tracks the constant by moving it to 45 and re-rendering.
- **The read is as non-load-bearing as the write.** `count_stealth_protections` opens its own session and swallows everything, for both of `log_shakedown_attempt`'s reasons: the table is allowed to be missing, and a failed query on a *borrowed* session poisons the caller's transaction. A perk count must never be able to take down the panel listing the perks. It returns 0, which renders as the old line rather than as a wrong number — and that path is tested by breaking the query outright, not just intended.
- **The tier gate lives in `_stealth_protections()`, not at the two call sites**, so neither can forget it and spend a query on a card that has no Stealth Mode line to put the answer on. `SYMBIOTE_PERKS` split into `SYMBIOTE_PERKS_STATIC` + `_stealth_mode_line()`; the new `stealth_protections` argument defaults to **0** all the way down, so every existing positional call still works and renders identically.

**3. And the rate the owner asked about landed at 0.30.** Same round, unrelated perk: *"we need to up the percentage a lil bit"* on Biomorphic Webbing's ambient scavenge, answered **0.30**. `AMBIENT_SCAVENGE_CHANCE` moved **0.20 → 0.30**, which puts the two components at **22.5% / 7.5%** per activity (the 3:1 weighting is the split, not the rate, so those per-item numbers moved on their own).

**The player-facing copy needed no edit, and that is the whole reason it was written the way it was.** `BIOMORPHIC_WEBBING_LINE` quotes no percentages at all — a deliberate choice made in round one after Venom Blast's hardcoded threshold went stale the moment its multiplier moved, and the ally-decay drawback before that. So a rate change touched the constant, three documentation comments, §9.3, and `check_ambient_scavenge.py`'s band, and nothing a subscriber reads. The check now asserts the rate as an **exact** value with the ±2.2pp band derived from it, so the next move has to come to that script and choose a new band rather than sliding under a tolerance that keeps passing. Measured after the change: **29.7% / 30.5% / 29.0%** across the three activities.

**0.30 makes this the perk's highest rate**, above the cash roll's 0.25 and the two combat rolls' 0.20, where it used to be tied for lowest. The old argument for 0.20 — one recognisable rate across all four rolls — was already false when it was written, since the cash roll has always been 0.25. What makes the new ordering defensible rather than merely instructed: **the two 0.20 rolls carry extra preconditions on top of the rate** (the component only rolls if the base drop already missed; the photo needs a camera equipped *and* a photo already banked) while this one fires on every completed activity with nothing else asked of it. A flat rate across rolls with unequal preconditions was never the same odds anyway.

**One correction to the numbers this decision was presented with.** The EV figures quoted while the choice was open — $19.50 → $29.25 per activity — are **catalog valuations, not income**. There is no NPC buyback anywhere in the game; `market_service` is player-to-player only, so the $80/$150 in `data/items.json` are shop *buy* prices and a surplus component cannot be turned into cash by the bot. What actually bounds the rate is the sink: **a repair consumes exactly one Spandex Fabric** (plus one Micro-Electronics past `suit_service.ELECTRONICS_THRESHOLD`) **regardless of how much integrity is missing**. So 0.30 buys a Symbiote subscriber repair self-sufficiency and adds supply to the player market. The fastest farm is giftless `/ally visit` — free, no cooldown, busy lock bottoming out at `MIN_VISIT_SECONDS` (30s) once the ally is happy, so ~120 rolls/hour by clicking, now ~36 components/hour instead of ~24. That loop predates the rate change and is bounded by the same one-item sink.

## Round seven — the DM Stealth Mode owed its owner

*"add the dm message whenever someone tries and shake down a symbiote user"*

Round six gave the perk a scoreboard on `/patreon perks`. This is the other half, and the ask is the right one: **a pull surface only helps someone who thinks to go and look, and nobody goes looking for a perk they don't know fired.** When Stealth Mode turns an attempt away, the target now gets a DM — which perk stopped it, who came looking, that nothing was taken, the 20-minute rule, and the same all-time count the card shows.

**Scope, stated plainly because it's narrower than the sentence might suggest.** The DM fires only when Stealth Mode **blocks** an attempt. A shakedown that *succeeds* against a Symbiote subscriber still tells them nothing, and that is a deliberate line rather than an oversight: being robbed while away is a gap that affects every player equally, so filling it is a game-wide feature (or a new perk), not part of making this one visible. Say so if the owner meant the broader thing — it's a small change to make, but it isn't this one.

**Naming the thief was the one call worth checking, and it leaks nothing.** `/shakedown`'s response is **not ephemeral** — the channel already saw a panel titled "Stealth Mode" that names the target and tells the thief *"Something's watching"* them and that they back off *"before you even get close"* — posted while the target was away. The DM reports a public message posted where they weren't looking, and who came sniffing is the only part with any value to them.

**§9's attribution rule runs in its normal orientation here**, unlike the thief's panel, which stays the codebase's one inversion: the reader *is* the payer, so the glyph leads and their own badge trails. **But the accent is the same trap round six hit, for the same reason and one step further out.** `_stealth_dm_view` is built inside the *thief's* command context, so `make_container()`'s ambient default would paint a subscriber's own perk DM in the thief's colour — or in no colour at all if the thief doesn't subscribe. It takes the accent explicitly.

Two details from that, both worth carrying forward. The parameter had to be named `target_tier_rank`, not `tier_rank`, because `check_symbiote_icons.py` asserts the literal string `accent_for_rank(tier_rank)` appears **nowhere** in `pvp_cog.py` — round six's own guard against reading the invoker's rank, which a plausibly-named new parameter would have tripped. **That's a check earning its keep in a way it wasn't written for**, and it was caught by reading the assertion rather than by running it. And the ambient default being *silently* wrong is now twice in a row on this one command; treat any new render inside `/shakedown` as accent-suspect by default.

**The throttle is the part that needed real thought.** The perk only fires while its owner is idle 20+ minutes, so a run of attempts during one absence would arrive as a **stack of near-identical DMs waiting for them** rather than as a live feed. One DM per 15 minutes per target, on a `cooldowns` row keyed `stealth_dm`. The real floor is tighter than that constant alone: `TARGET_PROTECTION_SECONDS` already caps any target at one attempt per 2 minutes from anyone, so 15 minutes turns a worst case of ~30 DMs/hour into at most 4, while an ordinary once-in-a-while attempt still always gets its own.

**Throttling is only acceptable because it's lossless in aggregate** — the DM quotes the **all-time** total, not "this is number N", so a subscriber attempted five times and DMed once still learns the true figure, and it's the same figure `/patreon perks` gives them.

Four smaller decisions:

- **The slot is claimed in the service, not the cog.** `claim_stealth_dm_slot` is named for its side effect: check-then-write has to be one step or two thieves resolving back-to-back both pass it. It sets `ShakedownResult.notify_target`, so the cog does only the Discord half and cannot forget the throttle.
- **Only the protected branch may consume the window** — and this is the one that would have quietly reintroduced the bug being fixed. If an ordinary shakedown burned it, the target would miss the next attempt the perk actually turned away, which is the only thing this DM exists to report. The check asserts an active Symbiote target and a non-subscriber leave **no `stealth_dm` row at all**, not merely an unexpired one.
- **It claims *after* the log write**, because the count in the copy has to include the attempt being reported.
- **Unlike round one's and round six's Stealth Mode helpers, this one takes the caller's session and is allowed to raise.** Those are telemetry, where losing a row beats failing a command. This is a throttle on player-visible behaviour, writing to a `cooldowns` table `/shakedown` already touches twice in the same transaction — a swallowed failure here would leave the throttle unset and DM on every attempt from then on, which is worse than the command failing.

**The send runs after `ctx.respond`, always.** Answering an interaction has a 3-second deadline and this needs a `fetch_user` round-trip plus a DM send; doing it first risks failing the thief's command in order to notify the target. Closed DMs are the *expected* failure (logged at info, not exception), and a bounced send still burns the 15-minute window — correct rather than merely tolerable, since closed DMs are a persistent state and releasing the slot would just mean retrying a doomed send forever.

**One test in this batch was written wrong first and is worth the mention.** The "a failed DM can't break the shakedown" checks were originally `check(label, True, True)` — which passes just as happily if the helper returns early and never touches Discord at all. They now assert against a stub that **records** that `send` was reached, and with which kwargs (`view` *and* `files`, or the thumbnail's `attachment://` URI has nothing to resolve against). A test whose failure mode is "passes for a reason unrelated to the claim" is the same family as round five's green `check_camera_gold` — that one asserted the wrong design, this one asserted nothing at all, and both agree with you either way.

`check_stealth_instrumentation` went **62 → 105 checks**. One of them is subtler than it reads: the 15-minute window is expired by **aging the row into the past**, not by lowering `STEALTH_DM_COOLDOWN_SECONDS` — the constant is only read when a slot is *claimed*, so lowering it wouldn't expire an already-open window and the test would have passed for the wrong reason.

## What each of the six actually did


**#1 — per-key rank map.** `ARACHNID_GATED_ITEM_KEYS` is gone; it's now `GATED_ITEM_MIN_RANK`, a `{item_key: min_rank}` map, with `GATED_ITEM_KEYS` *derived* from it for the callers that only ask "is this gated at all?" — so no second list has to be kept in step. (It lived in `shop_service` when it shipped; round two moved it to `patreon_service`.) `get_tier_rank()` stays the single chokepoint, and ranks are always compared with `>=` / `<`, never `==`, so a Symbiote subscriber automatically clears every Arachnid gate.

**#2 — the refresh loop.** `refresh_stale_links()` in `services/patreon_service.py` drains an oldest-checked-first queue; `SchedulerCog.patreon_tick` runs it every 15 min, 25 links per tick, re-reading anything past a 6-hour staleness window. The governing rule is written at the top of that section: **only a successful read of Patreon's identity endpoint may change a stored tier.** A 500, a 503, a DNS blip, a timeout — all fail open, stamp `last_checked_at`, and leave the tier exactly as it was. Erring this way means a lapsed pledge keeps perks for up to one extra interval, which is the right side to be wrong on.

The one exception is deliberate and necessary: a **4xx on the refresh grant** is Patreon stating the grant is gone, which no retry can fix, so that alone clears the tier (`_DeadLinkError`). Pure fail-open would have reopened the hole through the back door — an unverifiable credential would grant paid perks forever. The row is kept, so one `/patreon link` repairs it.

Two traps were caught before shipping and are both under test. Patreon **rotates the refresh token on every use**, so the new pair is committed *immediately*, before the identity call — otherwise a crash in between leaves a spent token stored and the next cycle declares a *paying* subscriber dead. And a refresh response that omits `refresh_token` retains the old one rather than blanking the field.

`RefreshOutcome` exists because a bare `tier: str | None` return cannot express the difference between "they have no pledge" and "we couldn't tell", and that distinction *is* the fail-open contract. `reached_patreon` is the load-bearing field.

**#3 — the Symbiote's own cost.** `SYMBIOTE_OVERRIDE_CHANCE` in `services/battle_service.py`: the suit takes over and attacks instead — no dodge, no combo banked. Shipped at **0.10, Evade-only**; round four moved it to 0.15 and added the gadget hijack; **round five doubled it again to 0.30**, which is where it stands. The reasoning that originally rejected 0.15 here (−7.87% on a boss, dropping a paying subscriber below the 70–75% an unsubscribed player with a full gadget kit gets) is now **history, not a gate** — 0.30 breaks it by a wide margin and shipped as an instructed decision. Nothing holds a "rejected" slot any more; the four-rate cost table in round five above is the whole record. Two other *shapes* were priced and rejected outright; those reasons are recorded in the comment so they don't get re-proposed.

**#4 — Venom Blast validated.** Simulated in `scratch/combat_sim.py`. Combat is a closed system, so this one *was* answerable by simulation, and the `2x` holds. **Round four left the multiplier alone and changed the trigger instead** (0 → 25% integrity, `scratch/check_venom_trigger.py`) — the `2x` is bound to the player-facing "twice as hard" copy, so it isn't a free knob; *when* the blast fires always was. **Round five changed *who* fires it**: the 25% bar is unchanged, but it now arms a button instead of triggering automatically, so the perk stopped being a death save (see round five above). The `2x` was re-measured under the button and still carries the whole perk — win rate across multipliers ×0–×4 runs **2.27% / 5.70% / 14.08% / 27.13% / 39.06%** at bracket 10, so ×2 → ×3 still nearly doubles it. The span narrowed a lot from the automatic era (~81 points to 36.79), but *"do not treat this constant as safe to nudge"* survives on its own merits.

**#5 — Stealth Mode made measurable, and deliberately NOT declared validated.** This is the honest outcome and it matters: the 20-minute threshold **cannot be settled by simulation**, because it depends entirely on how long real players step away from Discord. There's no ground truth to simulate against. So what shipped is the *measuring apparatus*, not a verdict:

- New `shakedown_attempts` table (migration `a7c41e93b508`). Before it, a stealth-protected attempt returned early and charged nobody — so it left **no trace at all**, not even a `transactions` row, and the perk's real firing rate was unobservable.
- `target_idle_seconds` is stamped on **every** attempt, protected or not. That's the design decision worth keeping: any *future* candidate threshold is scoreable from data already collected, instead of needing a fresh instrumentation deploy per number under consideration.
- The gate was split into a reading (`target_idle_seconds`) plus a pure predicate (`stealth_mode_active`) so the logged value is guaranteed to be the one the gate actually judged, and so the analysis script can replay the real rule rather than a copy of it. **Gate behaviour is unchanged** — every boundary is under test.
- Instrumentation is provably non-load-bearing, not merely intended to be: its own session, a blanket `except`, and tests that deliberately break the insert and assert the player's command still resolves and the cash still moves.
- **The constant was not touched, and the code says so** — `STEALTH_MODE_INACTIVITY_THRESHOLD_SECONDS` carries a `STILL UNVALIDATED` note pointing at the analysis script. **Round four changed nothing about the gate** — only that the refusal is now attributed, so a thief can tell it was somebody else's perk rather than a bug.

**#6 — Biomorphic copy scoped.** The perk advertised 3 rolls; 2 only fire in combat. Copy said "(combat patrols)" rather than the mechanic being changed, since the mechanic was right and the promise wasn't. **Round four reopened this and went the other way**: the owner's actual intent was that the webbing collects things *on the way* to Peter's other commitments, so a **fourth** roll now fires on `/tutoring`, `/ally visit` and `/bugle submit`, and the "(combat patrols)" qualifier was rewritten to scope only the two rolls that really are combat-only. Both passes were correct at the time — round one made the promise match the mechanic, round four made the mechanic match the intent.

## Verification pattern for this project — don't skip it

Run in this order; all of it was clean at the end of this session.

```bash
python -m compileall -q cogs services db utils alembic
```

Then load every extension end-to-end (**22** of them now — `v2_demo_cog` was deleted in round three) using the project venv — `.venv/Scripts/python.exe`, **not** bare `python`, which has no `discord` module:

```bash
./.venv/Scripts/python.exe -c "import discord, bot; b = discord.Bot(intents=discord.Intents.default()); [b.load_extension(e) for e in bot.EXTENSIONS]; print(f'{len(bot.EXTENSIONS)} loaded')"
```

**Neither of those two steps catches a shadowed import, and round five hit that twice.** Writing `scrap_note = ""` as a local in a function that also does `from services.shop_service import scrap_note` compiles fine, imports fine, loads all 22 extensions fine, and then raises `TypeError: 'str' object is not callable` the first time the branch runs. It happened once in `shop_service.buy_item` (caught by a check script, because that path has one) and once in `cogs/admin_cog.py`'s give-item branch (caught only by reading the file, because that path has none). The locals are named `scrapped_note` in both places now. **The general shape to watch for: a local whose name is the obvious one is often the imported helper's name too, and every cheap verification step is blind to it.**

Then the functional checks in `scratch/` (gitignored, so they live only in the working copy). Each builds a throwaway DB, drives the real service functions, and exits non-zero on failure. **Twelve of them now**, and all twelve were passing at the end of this session:

**A check script encodes the contract as of the day it was written, and round four proved that cuts both ways.** `check_override` *correctly failed* after the batch — it asserted `rate is 0.10`, `rate stays under 0.15`, and `SYMBIOTE_OVERRIDE_CHANCE is read in exactly one place`, all of which were true on 2026-08-23 and all of which the owner's decisions deliberately overturned. That's the script doing its job. The fix is to update it *and record why the old bar no longer binds* — the −7.87% that rejected 0.15 was measured against a configuration with the Sonic Dampener still in it. **A stale check that's silently relaxed to `>=` teaches nothing; one that's re-pointed at the new number with the reasoning attached is the whole value.** The "read in exactly one place" check is now "exactly two", kept as an exact count rather than `>= 1` so a third override surface can't be added silently — Attack must never become one.

**Round five is the other half of that lesson, and the more dangerous one.** `check_camera_gold` *passed* — and the bug was still shipped, because the assertion was `Silver ends up unequipped` and the design it encoded was itself wrong. A failing check argues with you. A passing one that asserts the wrong thing agrees with you, which is worse. There's no general defence, only a habit: **when a report and a green check disagree, the check is describing the code and the report is describing the product.** Go look at the surface the reporter was looking at — here, `/inventory`, where an unequipped $1,000 camera rendered with no annotation at all. The assertion is now `Silver is deleted, not kept unequipped`, and the ones next to it check the *receipt text*, because the surface is the thing that was broken.

**Two traps specific to that script, both of which produced false passes or wrong failures first:**

- **`os.environ.pop("PATREON_CLIENT_ID")` does not make a script offline.** `config.py` calls `load_dotenv()` at import, which copies `.env` into the environment *after* the pop. The first run therefore used the real credentials and fired four requests at Patreon with the fixture's junk tokens (rejected; only the throwaway DB was written). Blank the **module attributes** instead — `config.PATREON_CLIENT_ID = None` after `import config` — since `patreon_service` reads them at call time.
- **pycord keeps cog listeners in `Client._event_handlers`, not `bot.extra_events`.** The discord.py name doesn't exist here; `client.py`'s `dispatch` reads `_event_handlers.get("on_<event>")`. Private, but worth asserting separately from the dispatch itself so a failure distinguishes "never registered" from "registered and never ran".

**A source-grep assertion must strip comment lines.** Three of `check_revocation`'s checks failed on the first run for a reason worth remembering: they asserted that `"Swinging-Grade"`, `"Battle-Grade"` and `"silver lens"` no longer appear — and the comments explaining *why those labels were removed* naturally quote them. All four hits were comments. The script now filters lines starting with `#` before searching. Verifying a string's absence is the case where this bites; presence checks are unaffected.

**It bit again in round four, which is what makes it a pattern rather than an anecdote.** `check_symbiote_icons` asserts that `PatrolBattleView._render_final` doesn't hardcode a tier name — and that function's comments say "this used to hardcode Arachnid" and "told a Symbiote subscriber on a Gold body". The failure was in the *test*, not the code. It now shares a `_code_only()` helper whose docstring states the reason: matching comments makes the assertion unfalsifiable in either direction. **Anything asserting the absence of a string in Python source needs this from the start**, because the comment explaining a removal is exactly where the removed string lives on.

**Two more round-four traps in scratch scripts, both cheap to hit again:**

- **`-# ` breaks a naive "the glyph leads the line" check.** Discord's subtext marker has to come first or the line renders full-size, so `line.startswith(glyph)` fails on every subtext line even when the glyph is correctly placed. Strip the marker before asserting — it's markup, not content.
- **pycord's decorator replaces a cog method with a `SlashCommand` object**, so `inspect.getsource(SomeCog.some_command)` raises `TypeError: module, class, method, function... was expected`. Use `.callback`.

**And one about `combat_sim.py` itself, which is an exploration script rather than a check script (it exits 0 even with FINDINGS).** Round five left it reporting **six** findings where only one was about the shipped configuration: the floor check looped over every threshold in its own sweep, so a bar of 0% — which the button can never arm at, i.e. Symbiote paying the override's cost for a perk that never fires — of course sat under the free floor and got flagged. Five counterfactuals the script synthesized itself buried the one finding that meant something. It also blamed Venom Blast for a delta that was the whole *tier* toggled off vs on, override included, which would have sent the next reader to tune the wrong constant. Both are now fixed and it reports exactly 2, both real. **A FINDING has to mean "go look" — a sweep table is where counterfactuals belong, and a delta's label has to name what was actually toggled.**

**Every scratch script must set `SPIDEY_DB_URL` before anything imports `db.base`.** `config.py` reads `SPIDEY_DB_URL` — there is no `DATABASE_URL` — and it defaults to `./spidey.db`, so a script that sets the wrong name silently runs against the live dev database. Each script carries this as a comment.

Two more traps that cost time this session, both in scratch scripts rather than the app: **`User.reputation_level` is a read-only property derived from XP** — seeding a test user needs `reputation_xp=500_000`, and passing `reputation_level` raises `AttributeError: property ... has no setter`. And Python's `tempfile.gettempdir()` **is** safe for throwaway DBs despite the Git Bash `/tmp` gotcha below, because it returns a native Windows path; it's the *shell-provided* `/tmp/...` string that sqlite can't open.

Two Windows gotchas, both still true: **sqlite can't open a Git Bash `/tmp/...` path** (keep throwaway DBs inside the project dir), and a scratch script run from `/tmp` won't find the `services` package for the same reason. Standalone scripts need `sys.path.insert(0, '.')` since the repo root isn't installed. Also, the console can't print em-dashes or custom emoji — the `?` you see is a display artifact, not a data bug, but it **does** corrupt `Edit` `old_string` matching, so never build one from console output on this platform.

One coupling worth knowing before touching `db/base.py`: `async_sessionmaker(engine, expire_on_commit=False)` is **load-bearing** for `refresh_stale_links`, which commits per-link inside a loop over ORM objects. With expiry on, reading the next link's `access_token` would need implicit IO and raise `MissingGreenlet` under asyncio. The comment in `refresh_stale_links` says what to do if that setting ever changes.
